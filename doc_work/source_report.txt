036 [Heading 1] ABSTRACT
037 [Normal] AyurSathi is an Android wellness companion that presents Ayurvedic lifestyle information through a mobile interface backed by a REST API. The application lets users enter a health concern, request a response in a selected language, and view a structured result containing an Ayurvedic analysis, general health tip, home-remedy ingredients and preparation steps, yoga guidance, and advice on when to consult a doctor. It also includes a questionnaire-based Prakriti (dosha) self-assessment, recipe details, yoga instructions, settings for language and theme, and an app-version check.
038 [Normal] The mobile client is built with React Native and Expo. It communicates over HTTP with a Node.js and Express backend. The backend first checks an in-memory cache, then checks MongoDB for English-language remedy records, and then requests structured JSON from Google Gemini when a valid API key is configured. Generated responses are cached in memory and saved asynchronously to MongoDB. The application is therefore dependent on network connectivity and backend availability for symptom searches; the Prakriti questionnaire is computed locally in the app. This report documents the project requirements, architecture, implementation, data handling, and a verification plan. Test outcomes are not claimed where execution evidence is unavailable.
039 [Normal] Keywords: Android application, Ayurvedic wellness, React Native, Expo, Express API, MongoDB, Gemini AI, cache.

INTRODUCTION
071 [Heading 2] 1.1 Background
072 [Normal] Mobile applications have made digital wellness information easier to access. AyurSathi explores how a smartphone interface and a backend service can organize general Ayurvedic wellness content for users who want to learn about common concerns, home-remedy preparation, yoga, and lifestyle suggestions. The project combines an Android client with a server-side API that can retrieve cached results or request structured content from a generative AI service.
073 [Normal] The application is an educational software project. Ayurvedic suggestions and AI-generated text can be incomplete or unsuitable for an individual. The product includes doctor guidance and a disclaimer, and the report treats generated material as general information rather than clinical advice.
074 [Heading 2] 1.2 Problem Statement
075 [Normal] Users may encounter wellness information spread across unrelated sources and in languages they do not readily understand. A mobile application can provide a consistent way to submit a concern and display a structured response. The technical problem is to connect an Android interface to a backend that can request, validate at a basic structural level, cache, persist, and return remedy content while handling connectivity and service failures.
076 [Heading 2] 1.3 Aim and Objectives
077 [Normal] The aim is to design and implement an Android wellness companion supported by a backend API. Its objectives are:
078 [List Bullet] Provide a mobile search flow for a user-entered health concern.
079 [List Bullet] Return structured remedy, yoga, health-tip, Ayurvedic-analysis, and doctor-advice fields.
080 [List Bullet] Support language selection in the app and pass the selected language to the backend.
081 [List Bullet] Reduce repeated generation and database reads with an in-memory cache and MongoDB persistence.
082 [List Bullet] Provide a local Prakriti questionnaire, recipe and yoga detail screens, and configurable theme and language.
083 [List Bullet] Present basic app version information and handle network or backend errors clearly.
084 [Heading 2] 1.4 Scope

The project repository contains no website deliverable; web UI, web hosting, and browser-based product features are excluded. The backend may be deployed as a server service, but the user-facing client documented here is Android.

102 [Heading 1] CHAPTER 3
SYSTEM ANALYSIS AND DESIGN
103 [Heading 2] 3.1 System Architecture
104 [Normal] AyurSathi uses a client-server architecture. The Android application handles input, navigation, local questionnaire scoring, and presentation. The Express API accepts remedy requests and resolves them through an in-memory cache, MongoDB for English records, and the Gemini generation service. Mongoose maps remedy objects to MongoDB documents. The Android client receives JSON and routes the result to the Results screen.
105 [Normal] Android App (React Native / Expo)  →  Express REST API  →  In-memory cache / MongoDB / Gemini AI
106 [Heading 2] 3.2 Data Flow
107 [List Bullet] The user types a concern or chooses a quick ailment in HomeScreen.
108 [List Bullet] The client sends GET /api/remedies/{concern}?lang={language} to the configured API URL.
109 [List Bullet] The route normalizes the concern and language and checks the process-local cache.
110 [List Bullet] For English only, the backend checks MongoDB for a matching diseaseName.
111 [List Bullet] If no result is found and GEMINI_API_KEY is valid, the backend requests schema-shaped JSON from Gemini.
112 [List Bullet] The generated result is returned to the app, stored in the in-memory cache, and saved asynchronously in MongoDB.
113 [List Bullet] The app displays the result and gives access to remedy and yoga detail screens.

119 [Heading 2] 3.3 Backend API Design
120 [Normal] The remedy response includes diseaseName, ayurvedicAnalysis, healthTip, homeRemedies, yoga, and doctorAdvice. Each home remedy contains a name, ingredients, and preparation steps. Each yoga item contains a pose name, instructions, duration, image keyword, and YouTube search query. The route returns 502 when AI generation fails and 503 when no valid Gemini API key is configured; unexpected server errors return 500.
121 [Heading 2] 3.4 Database Design
122 [Normal] The Remedy Mongoose model stores diseaseName, healthTip, ayurvedicAnalysis, arrays of home remedies, arrays of yoga guidance, and doctorAdvice. Mongoose timestamps are enabled. The schema marks diseaseName as required and lowercase. The backend currently performs a database lookup only for English-language requests. AI-generated responses are saved asynchronously; persistence errors are logged and do not prevent the immediate response.

126 [Heading 1] CHAPTER 4
IMPLEMENTATION
127 [Heading 2] 4.1 Technology Stack
128 [Heading 2] 4.2 Android Client Implementation
129 [Normal] The app root composes ThemeProvider and LanguageProvider around the navigation container. App.jsx controls an animated splash screen and performs a version check against VERSION_API_URL. HomeScreen accepts free-text concerns and quick choices, passes the language as a query parameter, and navigates to Results with the returned object. It uses a request timeout and displays a user-facing alert for network, timeout, and backend errors.
130 [Normal] ResultsScreen, RecipeScreen, and YogaDetailScreen divide the response into readable sections and detailed views. PrakritiTestScreen contains six multiple-choice questions, increments one of three local scores per answer, and presents the highest-scoring dosha and corresponding lifestyle suggestions. ThemeContext and LanguageContext provide shared settings. No user account or authentication flow is present in the reviewed app structure.
131 [Heading 2] 4.3 Backend Implementation
132 [Normal] server.js loads environment configuration, enables CORS and JSON request parsing, connects to MongoDB, exposes health and version routes, and mounts remedyRoutes at /api/remedies. The remedy route normalizes the requested condition and language, checks an object-based in-memory cache, queries MongoDB for English results, then calls the Gemini API if configured. The prompt asks for a structured wellness response and the SDK receives a JSON response schema. The route retries selected rate-limit or overload failures with increasing delays.
133 [Heading 2] 4.4 Configuration and Deployment
134 [Normal] The backend configuration is provided through environment variables including PORT, MONGODB_URI, GEMINI_API_KEY, and optional GEMINI_MODEL. The repository includes a Render deployment descriptor. Secrets should be configured in the hosting environment and must not be committed in source control. The mobile API endpoint is controlled by the app configuration module. For local device testing, the configured address must be reachable from the Android device.
135 [Heading 2] 4.5 Error Handling
136 [Normal] The client distinguishes request timeout and network errors and displays a message from the API when available. The server returns JSON error messages for AI failures, missing API credentials, and unexpected errors. Database lookup/save failures are caught and logged in relevant paths. Operational validation should confirm that deployment logs do not expose secrets and that unavailable dependencies produce an understandable response.

152 [Heading 1] CHAPTER 6
SECURITY, PRIVACY, AND LIMITATIONS
153 [Heading 2] 6.1 Credential Handling
154 [Normal] The backend relies on environment variables for its database URI and Gemini API key. These values are sensitive and should be stored as deployment secrets. The repository contains an environment example file; the actual local environment file should remain excluded from source control. Production credentials must be rotated if disclosed.
155 [Heading 2] 6.2 Data Handling
156 [Normal] The remedy route sends the concern to Gemini as prompt input. The code sets store:false on the Gemini interaction request, indicating that interaction history is not requested to be retained by that call. The backend may persist generated remedy content in MongoDB; this implementation should not be described as storing no data. The reviewed app does not include user authentication or a personal health history feature. Logs and hosting/database access controls still require operational review.
157 [Heading 2] 6.3 Wellness Safety
158 [Normal] AyurSathi generates general wellness material and is not a diagnostic system. An AI-generated remedy may be inaccurate, inappropriate, or unsafe for a user’s conditions, allergies, pregnancy status, or medications. The app includes doctor advice and a disclaimer, but such text cannot guarantee clinical safety. Users should consult qualified health professionals, particularly for severe, persistent, or urgent symptoms. A production release should use expert review and stronger safeguards.
159 [Heading 2] 6.4 Current Limitations
160 [List Bullet] Symptom search requires network access and a reachable backend; there is no documented offline generation path.
161 [List Bullet] The process-local cache is not persistent across server restarts and may not be shared across multiple server instances.
162 [List Bullet] MongoDB retrieval is currently applied only to English-language requests.
163 [List Bullet] AI output quality, availability, latency, and quotas depend on the configured Gemini service.
164 [List Bullet] The local Prakriti questionnaire is a simple score tally and should not be represented as a clinical assessment.
165 [List Bullet] The reviewed repository does not include test evidence sufficient to claim the cases in Chapter 5 passed.

TABLE 24
Term | Definition in this project
Component | A reusable React Native UI unit. Screens such as HomeScreen and ResultsScreen are components.
Hook | A React function such as useState or useEffect that adds state or lifecycle behavior to a component.
Navigation stack | The registered set of screens through which the Android user moves.
Context provider | A React mechanism that makes shared values, such as theme or language, available to child screens.
REST API | The HTTP interface through which the app asks the backend for data.
Route | A backend handler connected to an HTTP method and URL, such as GET /api/remedies/:disease.
Schema | A definition of expected data fields and types; Remedy uses a Mongoose schema.
Cache | Temporary in-memory storage that can return a previously generated result quickly.
Model | A Mongoose object used to read and write documents that follow the Remedy schema.
JSON | The structured text format used to send remedy data between backend and app.
Environment variable | A runtime configuration value, such as GEMINI_API_KEY, kept outside source code.
Callback | A function passed to another function or hook; useCallback can preserve a function reference between renders.
